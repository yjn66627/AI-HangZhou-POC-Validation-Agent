## 锁定金句（路演只用这一句）

> 它不是普通聊天机器人。它回答的是：这件事到底证明到了什么程度，能不能上生产。

备选（不进主 PPT，仅备用）：

1. 把「AI 能不能上线」从主观判断，变成可复核的证据判定。
2. 系统会跑对照、收 Evidence，再给出档位；执行方不能自己宣布自己成功。

## 幻灯片结构

### 第 1 页｜标题

- 项目：AI POC 验证与技术决策智能体
- 赛事：AI杭州·超级智能体赛
- 副标题：用冻结的实验与 Evidence，决定能不能进入受控试运行

### 第 2 页｜痛点

企业 AI 最常见的失败不是「跑不起来」，而是「结论说过头」：

- 演示通了 → 宣布可以上生产
- 5 次过了 → 宣布稳定
- 质量达标 → 默认成本可控

### 第 3 页｜产品总流程

```
需求与约束 → 候选方案 → 实际运行/对照 → Evaluator → Evidence → Decision
```

评委一句话：先证据，后档位。

### 第 4 页｜系统架构（对外）

```
前端控制台 → Gateway → 实验执行 / 评估 → Decision Engine
```

- 前端：展示层，读稳定 ViewModel
- Gateway：统一出口（模型 / 工具 / 知识库）
- Evaluator：独立评估，证据不足则不允许通过
- Decision Engine：输出受控试运行 / 暂缓 / 证据不足 / 人工辅助 / 安全阻断

不在这页写内部实现术语。节点细节见 [`ARCHITECTURE.md`](ARCHITECTURE.md)。

### 第 5 页｜主 Case TEST-P1

问题：已有集成与质量数字，能不能宣布上生产？

已证明：集成、质量（LIVE-1R 5/5，质量 0.94 / 门槛 0.92）  
未证明：真实成本、延迟口径、生产并发、长期稳定性

### 第 9 页｜四列对比

| | 普通聊天机器人 | 只给 POC 建议 | 本系统 |
| --- | --- | --- | --- |
| 输入 | 一句闲聊 | 一份需求文档 | 带约束的 Formal Case |
| 过程 | 生成文字 | 生成方案 | 对照实验 + 独立评估 |
| 证据 | 无或不可复核 | 咨询式理由 | 结构化 Evidence |
| 结论 | 听起来能做 | 建议上线/再试试 | 冻结档位：受控试运行 / 暂缓 / 证据不足 |

第四列（评委追问用）：错误 Baseline = 「5/5 所以可以上生产」——系统拒绝该外推。

### 第 10 页｜现场 Demo

- 3 分钟：只跑 DEMO-S
- 5 分钟：加 DEMO-N 或 DEMO-U
- 失败：DEMO-F 或「模拟 LIVE 失败」

结论口径与 LIVE-1R 公开摘要一致。

### 第 11 页｜边界（主动说，建立可信）

- 当前主演示是已证明的 TEST-P1
- 真实 Tool 路径仍在验证，不拿未证明能力当主线
- 前端默认预置回放；不把健康检查当成真实实验成功
