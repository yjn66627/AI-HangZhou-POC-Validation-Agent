# TEST-R3｜知识库检索路径异常

> Case 编号：`TEST-R3`
> 类型：公开 Case（Tool 验证候选）
> 当前状态：`FIRST TOOL LIVE CANDIDATE`

---

## 一、现象

在同一输入、同一知识库的条件下，出现不一致：

| 观测路径 | 结果 |
| --- | --- |
| 知识库独立测试 | 能检索到结果 |
| Chatflow 知识检索节点 | 为空 |

同一份知识库，独立测能查到，放进 Chatflow 里就是空的。

---

## 二、为什么这不是一个"重启一下就好"的问题

这个现象至少存在多种可能原因，且彼此互斥：

1. 知识库绑定配置错误
2. Chatflow 节点输入参数未正确传递
3. 检索节点版本与知识库版本不匹配
4. 检索命中阈值设置过严
5. 实际调用发生了，但结果未被正确回传
6. 看似调用了，实际上没有发生真实调用

在没有真实调用轨迹之前，**以上任何一条都不能被宣布为根因。**

直接猜一个原因然后改代码，是最常见的错误处理方式。

---

## 三、未来 AI 必须完成的动作

面对这个 Case，系统必须按顺序真实执行：

```
1. 真实读取 KB 路径
        |
        v
2. 读取 Chatflow 配置 / 输入 / 版本
        |
        v
3. 获取真实 Tool Trace
        |
        v
4. 形成 Evidence
        |
        v
5. 再判断原因
```

关键约束：

- 步骤 1–3 必须是**真实读取**，不能基于猜测或历史缓存推断
- 步骤 4 必须形成可复核的 Evidence，而不是一句"我检查过了"
- 步骤 5 必须在 1–4 完成之后才能发生

**没有 Trace，就没有根因。**

---

## 四、判定标准

| 判定项 | 通过条件 |
| --- | --- |
| 路径读取 | 真实取得知识库路径，非推断 |
| 配置读取 | 真实取得 Chatflow 配置、输入参数、版本信息 |
| 调用轨迹 | 取得真实 Tool Trace，证明调用是否实际发生 |
| 证据形成 | 输出结构化 Evidence，可被第三方复核 |
| 结论顺序 | 先证据后结论，不允许先猜后补证据 |
| 不确定性表述 | 证据不足时明确说明"尚不能确定根因" |

---

## 五、这个 Case 的价值

TEST-R3 是 `FIRST TOOL LIVE CANDIDATE`，它把项目从：

> "结果对不对"

推进到：

> "过程可不可证明"

- 只关心结果：看到空结果，猜一个原因，改代码，再跑一次，碰对了就算过
- 关心过程：先拿到调用轨迹，确认调用是否发生，再定位差异，最后给出可复核结论

第二种才是可交付的技术决策能力。
