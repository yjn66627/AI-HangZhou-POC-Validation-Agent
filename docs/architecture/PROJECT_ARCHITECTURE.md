# 项目架构｜PROJECT ARCHITECTURE

> 本文档描述 **AI POC验证与技术决策智能体** 的整体架构与模块职责。
> 各模块当前处于不同验证阶段，请务必区分「已验证」与「尚在验证」。

---

## 一、端到端主链路

```
用户 / Case
   |
   v
+---------------------+
|      Backend        |  接收需求，创建实验，编排任务，持久化留痕
+---------------------+
   |
   v
+---------------------+
|      Gateway        |  统一出口：模型调用 / 工具调用 / 知识库检索
+---------------------+
   |
   v
+---------------------+
|    AI Executor      |  真实执行 Workflow（非模拟、非桩）
+---------------------+
   |
   v
+---------------------+
|   Workflow Result   |  结构化执行结果（状态、输出、耗时、调用记录）
+---------------------+
   |
   v
+---------------------+
|     Evaluator       |  独立评估：结果是否达标，是否可复现
+---------------------+
   |
   v
+---------------------+
|  Decision Engine    |  技术决策输出：支持 / 驳回 / 受控试运行
+---------------------+
   |
   v
+---------------------+
|    Comparison       |  跨 Case、跨版本横向比较，形成可对比结论
+---------------------+
```

一句话概括：
**需求 / Case → 实验 → Workflow Result → Evaluator → Decision Engine → Comparison**

---

## 二、逐段说明

### 1. 用户 / Case
一次验证的起点。Case 是可复现的、带明确预期的最小验证单元，而不是随便问一句。
Case 定义"我们要证明什么"，并显式列出"哪些事情本次不证明"。

### 2. Backend
- 接收 Case 输入
- 创建实验记录（谁、何时、哪个版本、什么参数）
- 编排后续链路
- 持久化全部执行留痕

### 3. Gateway
系统与外部能力的唯一出口：
- 模型调用
- 工具调用
- 知识库检索

统一出口的目的是：**所有外部调用都可被观测、被记录、被复现。**

### 4. AI Executor
真实执行 Workflow。
这里的关键词是「真实」——不是模拟返回值，不是桩函数，不是硬编码期望结果。

### 5. Workflow Result
结构化结果载体，至少包含：
- 执行状态（SUCCESS / FAILED）
- 输出内容
- 传输层结果（HTTP 状态）
- 执行时间
- 调用轨迹

### 6. Evaluator
**独立**评估环节，与执行环节分离。
它回答：这个结果是否达标？是否可复现？证据是否充分？
当证据不足时，采取 fail-closed 策略——**证据不完整，一律不允许通过**。

### 7. Decision Engine
把评估结果转成技术决策结论。当前决策档位包括：

| 结论 | 含义 |
| --- | --- |
| 支持 | 证据充分，可用于既定用途 |
| 受控试运行 | 集成与质量已达标，可进入受控范围试运行，但生产级指标未验证 |
| 驳回 | 证据不足或存在阻断性问题 |

### 8. Comparison
跨 Case、跨版本对齐比较，让"这一版比上一版好在哪、差在哪"变成可量化输出，而不是感觉。

## 四、为什么架构里要有 Evaluator 和 Decision Engine

只做"能跑通"的 AI 系统，和能做技术决策的 AI 系统，差别就在这里。

- **AI Executor** 负责"做出来"
- **Evaluator** 负责"判断做得好不好、证据够不够"
- **Decision Engine** 负责"据此能不能上，上到什么程度"

三权分立的目的是防止一种常见失败：
执行方自己宣布自己成功。

因此 Evaluator 必须独立于执行链路，Decision Engine 必须基于 Evaluator 的证据输出，而不是基于执行方的自述。

## 五、架构演进方向

1. 完成真实 Tool 验证，拿到完整 Tool Trace
2. 把 Evidence 从"结论级"提升到"过程级"
3. 建立成本与延迟的统一口径
4. UI / Demo 封装，形成可对外演示的完整体验
5. 比赛封版
